# 最XX的角色 9宫格

一个**单文件网页工具**：搜索 Bangumi 上的作品，把作品里的角色填进九宫格，最后导出一张带标题和制作人的 PNG 图。

- 单个 `index.html`，内联 CSS + JS，**没有任何构建步骤、没有 CDN、没有 npm 包**
- 双击 `index.html` 用浏览器打开就能用（`file://` 直接跑，不需要起服务器）
- 所有数据都从 Bangumi 公开接口实时获取，工具本身不联网保存、不收集任何数据

## 快速上手

1. 双击 `index.html`（Chrome / Edge / Firefox 均可）。
2. 右侧「① 搜索作品」输入作品名，回车或点「搜索」。中文、日文、英文都可以，例如 `little busters`、`命运石之门`、`CLANNAD`。
   - 注意：只搜**动画**（Bangumi 的 `type=2`）。
3. 点搜索结果里的作品，下面「② 选择角色」会列出这部作品的登场角色（立绘 + 名字）。
4. 点左边任意一个格子，再点右侧的某个角色，这个格子就填好了。
5. 填完点「导出 PNG」。**导出前必须填「制作人」。**

> 进度会自动存在浏览器的 localStorage 里，刷新页面不会丢（本地图片除外，见[已知限制](#已知限制)）。

## 格子规则

| 项目 | 规则 |
| --- | --- |
| 默认布局 | 3 列 × 3 行 = **9 格** |
| 列数范围 | **3 ~ 4**（用「列数 −/＋」按钮，或「加一列 / 减一列」） |
| 行数范围 | **3 ~ 10**（用「行数 −/＋」按钮，或「加一行 / 减一行」） |
| 最大格数 | 4 × 10 = **40 格** |
| 默认标签 | `最喜欢` `最遗憾` `最神秘` `最鬼畜` `最可爱` `最智慧` `最不正经` `最神人` `最败犬`（按从左到右、从上到下顺序填入） |

**标签怎么改、新格子的标签怎么来：**

- **默认标签可以随便改写**：直接**点格子左上角的标签文字**，它就会变成一个输入框，改完回车即可（Esc 取消）。
- **新增格子不会自动有标签**：超出前 9 格的格子标签是**空的**，显示为灰色的「点击写标签」，需要你自己写。界面上会提示还有几个格子没写标签。
- 不想逐个写的话，点「**补齐默认标签**」会把空着的格子按默认标签顺序补上（只补空的，不会动你改过的）。
- 标签最多 12 个字符；导出时长标签会自动截断成 `…`。

**其它操作：**

- **交换两格内容（两种方式，都支持）**
  - **拖动**：直接按住一个格子拖到另一个格子上松手。
  - **点击**：点亮「点击交换模式」，然后依次点两个格子。
  - 两者都是交换**角色**，标签留在原地不动（标签是「分类」，角色才是被比较的对象）。
- **清空一格**：选中格子后点右侧「清空该格」。
- **替换一格**：选中格子后点另一个角色即可替换。
- **清空所有角色**：顶部「清空所有角色」（保留标签）。
- **缩小布局**：如果被裁掉的格子里有角色，会先弹确认框，避免误删。

## 导出图片

点「导出 PNG」，工具用**浏览器原生 canvas** 合成图片（没有引入任何库）。

**导出图的内容：**

```
┌──────────────────────────────────────────────┐
│ 最XX的角色 9宫格                  ┌─────────┐│
│ 作品：Little Busters!             │制作人：XX││
│                                   └─────────┘│
├──────────────────────────────────────────────┤
│ ┌──────────┐ ┌──────────┐ ┌──────────┐      │
│ │ 最喜欢    │ │ 最遗憾    │ │ 最神秘    │      │
│ │ [ 立绘 ]  │ │ [ 立绘 ]  │ │ [ 立绘 ]  │      │
│ │ 直枝理树  │ │  棗鈴     │ │ 神北小毬  │      │
│ └──────────┘ └──────────┘ └──────────┘      │
│  … 共 9 格（或最多 40 格）…                   │
├──────────────────────────────────────────────┤
│ 角色立绘与资料来自 Bangumi（bgm.tv）  导出时间 │
└──────────────────────────────────────────────┘
```

- 每格结构：**标签胶囊（左上）→ 立绘 → 角色名（在图下方）**；名字下面还有一行小字显示日文原名（有中文名时）。
- 标题可以自己改（默认「最XX的角色 9宫格」）；标题下面会自动汇总这部作品里出现过的作品名。
- **制作人显示在右上角**，同时也可以在图里看出作者是谁。
- 导出尺寸：**2 倍图**。3×3 是 1540 × 2100 px；4×10 是 2028 × 6160 px。
- 文件名形如 `最XX的角色9宫格_制作人_20260919_1430.png`。

**「必须填制作人」是怎么强制的：**

1. 点导出时先读取「制作人」输入框并 `trim()`；**为空直接 return，不执行任何绘制和下载**。
2. 同时做三件事给出提示：输入框变红边框、输入框下方出现红字说明、右下角弹提示，并把焦点移回输入框。
3. 输入框失焦时也会校验一次，一开始打开页面就会提示「制作人还没填」。
4. 只有填了内容才会走 `buildCanvas()` → `canvas.toBlob()` → 触发下载。

另外提供了「**导出（不含立绘）**」按钮：只画标签和角色名，不画立绘。它是兜底用的——如果某些立绘因为跨域原因画不进画布，用它一定能导出成功。

**立绘清晰度**可选：

- **高清（large，默认）**：导出时取 Bangumi 的 `large` 尺寸，画质最好。
- **标准（medium）**：体积更小、取图更快。

（界面上网格里的缩略图固定用 `medium`，因为屏幕上的格子宽约 225px，正好和 medium 的约 220px 是 1:1，清晰又省内存。）

## 数据从哪来

全部来自 **Bangumi** 的公开接口（域名 `api.bgm.tv`），没有任何自建后端或第三方中转。

### 工具使用的接口

| 用途 | 接口 | 说明 |
| --- | --- | --- |
| 搜索作品（首选） | `POST https://api.bgm.tv/v0/search/subjects` | body `{"keyword":"…","filter":{"type":[2]}}`。这是 Bangumi 官方 v0 接口，但因为下面的实测原因，**在浏览器里几乎必然失败** |
| 搜索作品（降级） | `GET https://api.bgm.tv/search/subject/{关键词}?type=2&responseGroup=small` | 旧版公开接口，**带 `Access-Control-Allow-Origin: *`**，浏览器可直接读 |
| 取角色（首选） | `GET https://api.bgm.tv/v0/subjects/{id}/characters` | 返回角色的 `name` / `relation` / `images`（含 `grid`/`small`/`medium`/`large`） |
| 取角色（降级） | `GET https://api.bgm.tv/subject/{id}?responseGroup=large` | 返回里的 `crt` 字段就是角色数组，**带 CORS 头** |
| 角色立绘 / 作品封面 | `https://api.bgm.tv/pic/...` | 从接口返回的 `lain.bgm.tv` 地址**改写域名**而来（原因见下文） |

搜索时工具会**先试官方 v0 接口，失败自动降级**到旧版公开接口，并在界面上写出这次数据到底来自哪条路。取角色同理。

## 实测结论：跨域（CORS）与图片加载

以下都是**真实 HTTP 请求实测**的结果（并发过 Node.js，也发过伪造 `Origin` 头的请求来观察响应头）。

### 结论 1：`api.bgm.tv` 的 v0 接口不允许浏览器直接调用 ❌

**(a) `POST /v0/search/subjects`**

带 `Origin: https://example.com` 请求，得到的是 **HTTP 502**（Cloudflare 转发的 nginx 502 页面），响应里**没有任何 `Access-Control-Allow-Origin`**：

```
HTTP/2 502
content-type: text/html
server: cloudflare
cf-cache-status: DYNAMIC
（响应体是 <html><head><title>502 Bad Gateway</title>…nginx/1.18.0 (Ubuntu)）
```

探测期间该路由**即使不带 `Origin` 也是 502**（对同一路径发 GET 同样 502），说明这条接口当时本身就不健康。而且 `POST` + `Content-Type: application/json` 会触发**预检 `OPTIONS`**，`OPTIONS` 返回的也是 502 —— 也就是说浏览器连预检这一步都过不去。

**(b) `GET /v0/subjects/{id}/characters`**

这条更关键，因为它能正常返回数据，但**一加 `Origin` 就挂**。做了严格的交替 A/B 测试（每种情况各 6 轮）：

| 请求 | 结果 |
| --- | --- |
| **不带** `Origin` | **200**，39997 字节，19 个角色 —— **6/6 成功** |
| 带 `Origin: https://example.com` | **502**（166 字节 nginx 502 页）—— **0/6 成功** |
| 带 `Origin: null` | 502 |
| 带 `Origin: https://bgm.tv` | 502 |
| 只带 `Referer: https://bgm.tv/`（无 Origin） | 200 ✅ |
| `Referer` + `Origin` 同时带 | 502 |

而且即使是返回 200 的那次，响应头里**也没有 `Access-Control-Allow-Origin`**。

**结论：** 浏览器发 `fetch()` 时**一定会带上 `Origin` 头**（跨域请求必带），所以这个接口在浏览器里**必定失败**——不是因为"缺 CORS 头"，而是因为**带了 `Origin` 就直接 502**。

**排除环境干扰：** 用完全相同的 `Origin` 头请求 `https://api.github.com/`，正常返回 200 且带 `Access-Control-Allow-Origin: *`。所以这不是本机网络或代理的问题，是 Bangumi 服务端的行为。

### 结论 2：旧版公开接口**允许**浏览器直接调用 ✅

对照实测，这几个老接口都带 `Access-Control-Allow-Origin: *`，而且是简单的 GET（不触发预检），浏览器可以直接读取：

| 接口 | 结果 |
| --- | --- |
| `GET /search/subject/little%20busters?type=2&responseGroup=small` | **200**，`Access-Control-Allow-Origin: *`，返回 5 部作品 |
| `GET /search/subject/命运石之门?type=2&responseGroup=small` | **200**，`ACAO: *`，`results: 42` |
| `GET /subject/38040?responseGroup=large` | **200**，`ACAO: *`，含 `crt` 12 个角色 |
| `GET /calendar` | **200**，`ACAO: *` |

**所以工具的主力数据通道是这些旧接口**，v0 接口保留为"先尝试"，一旦它恢复可用就会自动走 v0。

### 结论 3：`lain.bgm.tv` 的图片**不需要 Referer**，但**没有 CORS 头** ⚠️

**不需要 Referer** —— 三种情况都正常返回（`image/jpeg`，`cache-control: max-age=2592000`）：

| 请求 | 结果 |
| --- | --- |
| 不带 `Referer`、不带 `Origin` | **200** ✅ |
| 带 `Referer: https://bgm.tv/` | **200** ✅ |
| 带 `Origin: https://example.com` | **200** ✅（但响应里没有 ACAO） |

所以 `lain.bgm.tv` 的图**能正常显示**（`referrerpolicy="no-referrer"` 加上只是更保险，不是必需的）。

**但是 `lain.bgm.tv` 不返回任何 CORS 响应头**，这带来一个很实际的麻烦：

- 用 `<img crossorigin="anonymous">` 加载 → 浏览器校验 CORS 失败，**图根本加载不出来**
- 用普通 `<img>` 加载 → 能显示，但把这个 `<img>` 画进 canvas 会**污染画布**，`canvas.toBlob()` / `toDataURL()` 会抛 **`SecurityError`**，PNG 就导不出来

### 结论 4（关键发现）：把图片域名换成 `api.bgm.tv` 就能拿到 CORS ✅

实测发现，**同一个图片路径换成 `api.bgm.tv` 域名后，响应会带上 `Access-Control-Allow-Origin: *`**：

| 图片地址 | 结果 |
| --- | --- |
| `https://lain.bgm.tv/pic/crt/g/f7/c2/357_crt_4H84e.jpg` | 200，**无 ACAO** ❌ |
| `https://api.bgm.tv/pic/crt/g/f7/c2/357_crt_4H84e.jpg` | 200，**`ACAO: *`** ✅ |
| `https://api.bgm.tv/pic/crt/l/ac/ef/358_crt_375d8.jpg` | 200，`ACAO: *`，JPEG 800×2767 ✅ |
| `https://api.bgm.tv/pic/cover/g/46/ea/38040_KFMP9.jpg` | 200，`ACAO: *` ✅ |

共验证 5 张图（角色立绘的 grid / medium / large、作品封面），**全部带 `ACAO: *`**，且都是合法 JPEG（校验过 JPEG magic bytes 和实际像素尺寸）。

**这就是「导出带立绘的 PNG」能成立的原因。** 工具里的 `normalizeImg()` 会把接口返回的 `http://lain.bgm.tv/...` 统一改写成 `https://api.bgm.tv/...`（顺便把 `http` 升级成 `https`、把尺寸段 `s/g/m/l` 换成需要的尺寸）。这样 `<img crossorigin="anonymous">` 能通过校验，canvas 不被污染，`toBlob()` 正常导出。

> 这个发现也让「用本地图片兜底」成了第二重保险：万一以后 `api.bgm.tv/pic/` 这条路失效了，还可以对出问题的格子点「该格用本地图片」，本地文件不受跨域限制，导出一定包含它。

### 图片尺寸实测（决定工具用哪个尺寸）

| 尺寸段 | 实测像素 | 备注 |
| --- | --- | --- |
| `/s/` | 48 × 48 | 太小 |
| `/g/` (grid) | 75 × 75 | 缩略图用 |

## 接口不通时怎么用：粘贴 JSON 降级方案

因为上面结论 1 的原因，v0 接口在浏览器里很可能是失败的。工具已经内置了自动降级（走结论 2 的旧接口），正常情况**你不需要做任何额外操作**。

但如果**两条路都失败了**（比如接口临时故障、网络环境限制），界面上会出现红色提示。这时用**粘贴 JSON** 的路子——它的原理很巧妙：

> **在地址栏直接打开接口地址是「普通导航请求」，浏览器不会带 `Origin` 头**，所以接口能正常返回 JSON；而在网页里用 `fetch()` 会被加上 `Origin` 头，这正是它会 502 的原因。

### 步骤

**① 要「作品列表」：**

在浏览器新标签打开（把「关键词」替换成你要搜的名字，中文可以直接写在地址里）：

```
https://api.bgm.tv/search/subject/关键词?type=2&responseGroup=small
```

例如 `https://api.bgm.tv/search/subject/little%20busters?type=2&responseGroup=small`

页面上会直接显示一段 JSON，**全选复制**。

**② 要「某部作品的角色列表」：**

先在 Bangumi 网页上找到作品，记下地址里的数字 ID（形如 `bgm.tv/subject/38040` 里的 `38040`），然后新标签打开：

```
https://api.bgm.tv/v0/subjects/作品ID/characters
```

也可以打开 `https://api.bgm.tv/subject/作品ID?responseGroup=large`（旧接口，同样能拿到 `crt` 角色数组）。工具在选中作品后，右侧会出现「**在新标签打开当前作品的角色接口 ↗**」的链接，直接点它就行。

**③ 粘贴：**

把复制到的 JSON 粘到右侧「接口不通时：粘贴 JSON 继续用」的文本框里：

- 点「**当作「作品列表」解析**」→ 上面会出现作品列表，点作品即可继续
- 点「**当作「角色列表」解析**」→ 上面会出现角色卡片，点角色即可填进当前格子

**支持的 JSON 形状（会自动识别）：**

| 类型 | 支持的形状 |
| --- | --- |
| 作品列表 | `{"data":[…]}`（v0 搜索）/ `{"list":[…]}`（旧搜索）/ `[…]` |
| 角色列表 | `[{name, images, relation, …}]`（v0 角色）/ `{"crt":[…]}`（旧接口作品详情）/ `{"data":[…]}` |

`images` 写成字符串（而不是对象）也能识别。

## 已知限制

1. **没有在真实浏览器里实测过。** 我在这个环境里没有浏览器可用，所以无法真实点击、拖动、导出。为了把风险降到最低，我做了这些事：
   - 把 `index.html` 里内联的 `<script>` 抽出来单独跑 `node --check`，语法检查通过；
   - 用一个桩 DOM 在 Node 的 `vm` 里**真的执行了一遍这个脚本**，初始化、渲染、扩格、解析、排版绘制全都跑通；
   - 用**真实 Bangumi 返回的数据**（19 个角色的 v0 JSON、12 个角色的旧接口 JSON、搜索 JSON）测了解析和 URL 改写；
   - 用桩 canvas 跑完了 `buildCanvas()` 的全部绘制代码路径，验证 3×3 和 4×10 的排版尺寸；
   - 真连 Bangumi 跑通了「搜索 → 选作品 → 取角色」的完整数据链和自动降级逻辑；
   - 交叉检查了 JS 里引用的 33 个 element id 是否都在 HTML 中存在。
   即便如此，**视觉呈现（字体、间距、拖动手感）和实际导出的像素效果仍未经人眼确认**，可能需要在浏览器里微调。

2. **旧接口的角色数可能少于 v0。** 实测作品 38040：v0 返回 19 个角色，旧接口的 `crt` 只有 12 个。想拿到完整列表，可以用「粘贴 JSON」的方式打开 v0 角色接口再粘贴进来。

3. **网页无法设置 `User-Agent`**（浏览器禁止脚本修改该请求头），只能用浏览器自身 UA。需要自定义 UA 请用 `curl`/Node 抓 JSON 后粘贴。

4. **v0 接口的状态可能随时变化。** 探测时 `/v0/search/subjects` 整体 502、`/v0/subjects/{id}/characters` 带 `Origin` 就 502；这些都是**当时**的实测结果。工具总是先试 v0 再用旧接口兜底，所以接口恢复后会自动走 v0，无需改代码。但如果 Bangumi 之后改了路径或返回结构，工具可能失效——`normalizeImg()` 的域名改写也依赖 `api.bgm.tv/pic/` 这个路径继续存在。

5. **立绘原生分辨率有限。** Bangumi 的角色立绘常见只有 220~250 px 宽（也有 800 px 的），导出是 2 倍图，所以立绘可能会被放大而显得略软。这是数据源本身的限制，改用「标准」清晰度可以让放大比例更小。

6. **非 Bangumi 域名的图片可能导不出来。** 如果你粘贴的 JSON 里图片地址不是 `lain.bgm.tv` / `api.bgm.tv`，而那个域名又没有 CORS 头，图能显示但画不进画布；导出时会用占位色块代替并在提示里说明。解决办法：对那个格子点「该格用本地图片」。

7. **本地图片不会被保存。** 本地图片用的是 `blob:` URL，刷新页面后失效，需要重新指定。localStorage 里只保存远程角色数据、标签、标题和制作人。

8. **只搜动画**（Bangumi `type=2`）。搜不到游戏、书籍、音乐条目。

9. **没有撤销/重做**，也没有排序功能。

10. **导出尺寸较大**：4×10 的导出图是 2028 × 6160 px，格子多、立绘大时合成需要几秒，期间按钮会显示「正在合成…」。
